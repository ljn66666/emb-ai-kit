# ESP32 / STM32 接大模型 · 中文实战手册

配套工程：`emb-ai-kit`（MIT 开源）
适用硬件：Seeed XIAO ESP32S3 Sense + MAX98357A + SG90 ×4（其它 ESP32 板可平移）

---

## 0. 这份手册是什么

把散在四个英文 README 里的东西，压成一条能照着走完的路径，加上逐脚接线表、供电预算表、排错对照表。

英文 README 告诉你「有个坑」。手册告诉你「你现在这个现象，是不是这个坑，怎么一分钟验证，怎么改」。

全文免费，随代码一起 MIT 发布。不用付钱，不用注册。

> **内容来源**：本手册由 AI 辅助撰写，其中的故障现象、接线方式、供电数据与代码，均由作者在真实硬件上逐条验证。手册随代码以 MIT 协议发布。

**这份手册不解决的问题**：不会 C++、没用过 PlatformIO、没烧过固件的人，先补这三样再来。

## 1. 三层桥接长什么样

```
┌──────────────┐   带帧串口    ┌──────────────┐   HTTP / stdio   ┌─────────────┐
│   固件层      │ ───────────▶ │   主机桥      │ ──────────────▶ │  大模型 / MCP │
│ ESP32 / STM32 │ ◀─────────── │   Python     │ ◀────────────── │ Claude / …   │
└──────────────┘              └──────────────┘                  └─────────────┘
```

三层各自的职责，**不能混**：

| 层 | 干什么 | 绝对不能干什么 |
|---|---|---|
| 固件层 | 读传感器、驱动舵机、收发带帧串口 | 不能持有 API Key |
| 主机桥 | 唯一接触 API Key 的一层；把串口事件翻成模型调用，把工具调用翻成串口指令 | 不能直接碰 GPIO |
| 大模型 / MCP | 决策、生成动作 | 不能直连串口 |

API Key 放在固件里，是把密钥烧进一台会被人拿走的设备。

## 2. 硬件清单

| 数量 | 元件 | 备注 |
|---|---|---|
| 1 | Seeed XIAO ESP32S3 Sense | 主控 + 板载麦克风 |
| 4 | SG90 舵机 | 5V，单颗堵转约 700 mA |
| 1 | MAX98357A 模块 | I2S 转喇叭 |
| 1 | **5V / ≥3A 独立电源** | **只给舵机，不给主控** |
| 1 | 470 µF 电解电容 | 跨接在舵机电源 5V 与 GND 之间 |
| — | 杜邦线、面包板或洞洞板 | |

**那颗 470 µF 不是可选项。** 它吸收舵机启动瞬间的浪涌，能把"偶尔重启"变成"基本不重启"。

## 3. 接线（逐脚）

### 3.1 舵机

```
舵机 1 信号 → D1      舵机 2 信号 → D2
舵机 3 信号 → D3      舵机 4 信号 → D4
（D5 / D6 / D7 可继续接 5~7 号舵机）

舵机 VCC（红线）→ 独立 5V 电源正极
舵机 GND（棕线）→ 独立 5V 电源负极
独立 5V 电源负极 → 同时接到 XIAO 的 GND      ← 这根线是全篇最重要的
```

**D0 必须空着。** D0 落在 strapping 相关引脚上，接舵机会在上电瞬间被甩角度。

### 3.2 MAX98357A（I2S 音频）

```
BCLK  → GPIO12
LRCLK → GPIO13
DIN   → GPIO14
Vin   → 5V（3.3V 也能驱动逻辑）
GND   → 与主控共地
```

### 3.3 电源拓扑

```
USB 供电 ──▶ XIAO（主控）
5V/3A 电源 ──▶ 舵机 ×4 ＋ 470µF
                    │
                    └──── GND ────▶ XIAO GND（共地）
```

**禁止**：从 XIAO 的 5V 脚给舵机供电。USB 2.0 口只有 500 mA 预算，一颗 SG90 堵转就要 700 mA，四颗同时动是数学上不可能。

## 4. 五个坑（按踩到的概率排序）

### 坑 1｜一动就重启 —— 舵机和主控共用 5V

**症状**：台面上静止时一切正常，一发指令让舵机动，ESP32 立刻重启。串口打印里能看到 brownout 之类的复位原因。

**原因**：舵机启动瞬间的浪涌电流把 5V 拉塌，主控欠压复位。

**一分钟验证**：万用表接在 5V 和 GND 之间，眼睛盯着，发一条让 4 颗舵机同时动的指令。电压往下掉超过 0.3V 基本就是它。

**改法**：舵机换成独立 5V/≥3A 电源。

**预算公式**（真机上验证过的经验值）：

```
峰值需求 ÷ 可用电流 < 70%   → 稳
70% ~ 120%                  → 时好时坏
> 120%                      → 必重启
```

四颗 SG90 × 0.7A = 2.8A，接 3A 电源 = 93%，落在"时好时坏"区间——所以还要配合坑 5 的错峰调度。

---

### 坑 2｜随机抖、串口乱码 —— 双电源不共地

**症状**：台面上好的，装进外壳就开始抖；或者串口偶尔收到乱码。查代码查不出来。

**原因**：两路电源没有共同参考地，电平判定悬空。

**改法**：舵机电源的 GND 用一根线接到主控 GND。

**这一根线能解决大约 80% 的"灵异"问题。** 遇到说不清的现象，先确认共地，再怀疑代码。

---

### 坑 3｜上电瞬间舵机乱甩 —— 挂在 strapping 引脚上

**症状**：一通电，舵机不是回中位，而是猛地甩到一个随机角度，然后才正常。

**原因**：ESP32 的 GPIO0 / GPIO2 / GPIO15 在上电时被采样，用来决定启动模式。舵机挂在这些脚上，采样期间的抖动会被当成 PWM 信号。

**改法两层**：

1. 硬件层：舵机只接 D1–D7，D0 留空。
2. 固件层：在 attach PWM 通道**之前**，先把每个舵机脚的 idle 值写成 1500 µs（中位）。这样即使有毛刺，也不会甩。

```cpp
// 顺序不能反
writeIdle(pin, 1500);   // 先定静默态
attachServo(pin);       // 再挂通道
```

**这个坑固件修不好，只能靠选对引脚 + 定义 idle。** 引脚选错，代码写得再漂亮也没用。

---

### 坑 4｜I2S 音频咔哒声 / 断续

**症状**：喇叭里有规律性的咔哒，或者播到一半断掉。

**原因**：BCLK / LRCLK 与主控之间的时钟偏斜，或者 DMA 缓冲欠载。

**改法**：

- I2S 的几根线走短，别绕远、别和舵机线捆一起
- 采样率显式写死，不要靠默认值
- DMA 缓冲区按你的帧长来算，别用示例里的默认值
- 板载麦克风（Sense 版）是最省事的路；外接 INMP441 在不同批次间一致性更好

---

### 坑 5｜串口丢一个字节，整条链路永久失步

**症状**：跑一阵子之后，指令开始错位——发的是 2 号舵机，动的是 3 号；或者干脆没反应，重启又好了。

**原因**：用了裸字符串协议（比如直接发 `angle=90`）。只要丢一个字节，解析器就永久错位。

**改法**：换成带定界的帧协议。工程里用的是：

```json
{"cmd":"move","id":2,"us":1500}\n
```

关键是那个 `\n`——解析器以它为同步点，丢字节后在下一条消息重新对齐，而不是永久失步。

**判断你现在的协议有没有问题**：拔掉再插上串口，如果恢复，说明没有重同步机制，只是碰巧对齐了。

## 5. 上手四步

### 第 1 步：烧固件

```bash
cd examples/serial_voice_agent/firmware
pio run -t upload
```

PlatformIO 会自动拉 ESP32 平台包。第一次编译慢，正常。

### 第 2 步：跑主机桥

```bash
cd examples/serial_voice_agent/host
pip install -r requirements.txt
python bridge.py --port COM3        # Windows 换成你的实际串口
```

Linux / macOS 用 `/dev/ttyUSB0` 或 `/dev/ttyACM0`。

API Key 用环境变量传，不要写进代码：

```bash
# Windows PowerShell
$env:OPENAI_API_KEY="sk-..."
# Linux / macOS
export OPENAI_API_KEY=sk-...
```

### 第 3 步：说一句话

在 bridge 的输入里敲：

```
wave hello
turn to the left
```

流程是：bridge 调模型 → 拿到 JSON 动作 → 写进串口 → 固件驱动舵机。

**第一次跑建议先只接 2 颗舵机**，确认链路通了再加到 4 颗。四个一起上，出问题你分不清是协议、是电源、还是引脚。

### 第 4 步：挂成 MCP 服务

让 Claude / Cursor 这类客户端直接调用你的硬件：

```bash
# 先不接硬件，纯测试
python mcp-device-server/server.py
```

没有硬件时，每个工具都会返回 `[simulated]`，用来验证客户端配置对不对。

接真硬件：

```bash
python mcp-device-server/server.py --port COM3
```

客户端配置（以 Claude Desktop 为例，`claude_desktop_config.json`）：

```json
{
  "mcpServers": {
    "emb-ai-kit": {
      "command": "python",
      "args": [
        "C:/绝对路径/mcp-device-server/server.py",
        "--port", "COM3"
      ]
    }
  }
}
```

连上后客户端会看到三个工具：

| 工具 | 作用 |
|---|---|
| `move_servo` | 按脉宽（500–2500 µs）驱动一颗舵机，带范围校验，不会甩到极限 |
| `read_sensor` | 读设备侧传感器值（麦克风电平、距离、ADC…） |
| `center_all` | 所有舵机回中位，上电调用是安全的 |

## 6. 排错对照表

| 现象 | 最可能的原因 | 一分钟验证 | 改哪 |
|---|---|---|---|
| 一动就重启 | 共用 5V，欠压 | 万用表盯 5V，发四舵机同时动 | 独立 3A 电源 + 470µF |
| 上电甩角度 | 舵机在 strapping 脚 | 看接线是不是用了 D0 | 换 D1–D7，先写 idle 再 attach |
| 随机抖 / 乱码 | 没共地 | 量两路电源 GND 是否导通 | 一根线连 GND |
| 跑一阵就失步 | 裸字符串协议 | 拔插串口看是否恢复 | 换定界帧协议 |
| 音频咔哒 | 时钟偏斜 / DMA 欠载 | 缩短 I2S 走线试试 | 显式采样率 + 重算缓冲 |
| 舵机不动 | 信号线没接对 / 电源没开 | 单独测一颗舵机 | 先排除硬件 |
| 只有 1 颗能动 | 电源电流不够 | 拔掉 3 颗再试 | 换 ≥3A 电源 |
| MCP 客户端看不到工具 | 配置路径不对 | 不带 `--port` 先跑一遍 | 用绝对路径 |

## 7. 服务预算表（抄下来贴在工位上）

| 舵机型号 | 堵转电流 | 4 颗峰值 | 建议电源 |
|---|---|---|---|
| SG90 | ~0.7 A | 2.8 A | 5V / 3A |
| MG90S | ~0.9 A | 3.6 A | 5V / 5A |
| MG996R | ~2.5 A | 10 A | 5V / 12A，且必须错峰 |

按 70% 安全线算，4 颗 SG90 接 3A 电源时，**同一时刻最多 3 颗在动**，第 4 颗排队。

配套的 `servo-stabilizer` 就是干这个的：它算并发预算，超了就返回 `false` 让你下一拍重试。

```cpp
if (!stab.requestMove(2, 2000)) { /* 下一拍再试 */ }
stab.update();   // 每次动作稳定后释放预算
```

## 8. 想加自己的工具

`mcp-device-server/server.py` 里的 `build_tools()` 是个列表，每项三个字段：

- 工具名
- JSON Schema 的 `inputSchema`
- 处理函数（收到解析后的 `arguments` 和一个 `DeviceConnection`）

固件侧对端在 `examples/serial_voice_agent/firmware/src/main.cpp`。加一个工具 = 改两处，不用动传输层。

**传输层用的是标准库手写的 JSON-RPC 2.0**，没有第三方依赖，所以任何有 `python3` 的机器都能跑。只有真接硬件时才需要 `pyserial`。

## 9. 附录：常见板子引脚平移

| XIAO ESP32S3 | 常见 ESP32 DevKit | 说明 |
|---|---|---|
| D1–D7 | GPIO 任意可用脚 | 避开 GPIO0 / 2 / 15 |
| GPIO12 / 13 / 14 | 同编号 | I2S 三根线 |
| D0 | 不要用 | strapping 相关 |

换板子时唯一要守的规矩：**舵机别碰 strapping 脚，D0 类别空着。**

## 10. 跑不通怎么办

在仓库开 issue，写清三件事：

1. 用的什么板子、什么舵机、几颗
2. 电源是怎么接的（有没有独立 5V、有没有共地）
3. 串口打印的**完整**报错

九成的「跑不通」在前两条里就能看出来。

要按你的具体硬件改一版（不同主控、不同舵机数量、要接自己的传感器、要接自己的模型），在 issue 里说，我看到会回。
